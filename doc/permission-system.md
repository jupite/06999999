# 用户权限管理系统

更新日期为 2026-11-12。用户权限和项目网站名单管理已接入。

## 当前使用

1. 站主从「站点管理 → 用户权限管理」进入。可按昵称或 GitHub 数字 ID 搜索，并按账号状态、功能或允许和禁止名单筛选。
2. 打开用户详情，逐项选择「继承默认」「允许」或「禁止」并保存。详情会显示最终生效权限和原因，也可跳转到同一用户的图片配额设置。
3. 普通账号可封禁或解封。封禁使已有站内登录会话失效，解封后用户需重新登录。站主账号受保护。
4. 最近十条权限、账号状态和图片额度操作会显示操作者、时间及变更前后值。改动后，下次请求会重新读取权限。审核通过前会重新检查作者当前的投稿资格。

图片授权与图片额度共用原有数据。作者被封禁或撤权后，已发布内容仍可供访客浏览，待审稿件保留在审核队列中。部署前运行 `pnpm db:deploy`，添加会话版本字段和审计查询索引。

用户列表采用后台表格，展示账号、状态、个人允许/禁止项数和图片用量；没有个人配置时显示继承默认。手机端可在表格区域横向滚动。

## 已确认范围

- 增加统一用户权限管理，支持分别设置权限、白名单和黑名单。
- 保留统一图片上传权限，覆盖所有图片上传入口；每用户独立容量上限。
- 保留项目网站白名单，以及其他用户内容统一 AI 初审、人工兜底的要求。

## 已确认权限规则

用户已明确同意以下四条规则：

1. 账号封禁优先，显式禁止优先。
2. 白名单只赋予操作权限，不能绕过容量、项目网址限制或 AI 审核。
3. 图片上传保持统一权限，不拆成不同栏目的上传开关。
4. 后台显示权限生效原因，便于解释用户能否发布。

站主与普通用户的默认权限见下表。尚未开放的栏目能力可以预先配置。

项目域名规则已确认：后台维护允许域名，默认精确匹配，可逐条开启包含子域名；未匹配则禁止提交。

## 角色与单用户设置

首版采用站主和普通用户两种角色。无需提前建设任意角色编辑器；后续确有协作者时再增加审核员等角色。

每项能力对单个用户提供“继承默认 / 允许 / 禁止”三种状态：允许形成该功能用户白名单，禁止形成黑名单；清除配置恢复默认。不要用两个独立开关制造同一用户同时允许和禁止的歧义。

| 能力                         | 推荐普通用户默认行为                                       |
| ---------------------------- | ---------------------------------------------------------- |
| 提交文章                     | 允许，进入审核                                             |
| 点赞/取消点赞                | 建议登录后允许，仅操作可访问的公开内容，不进入审核         |
| 提交评论                     | 允许，进入审核；站主本人免审                               |
| 提交项目卡片                 | 允许，须符合网站白名单并进入审核                           |
| 添加音乐                     | 仅站主在音乐管理后台导入                                   |
| 提交友链                     | 允许，进入审核                                             |
| 提交照片墙内容               | 默认允许提交，但必须同时具备图片上传权限；不能绕过资源授权 |
| 上传图片                     | 默认关闭，站主允许并设置容量后开放                         |
| 编辑/删除自己的内容          | 默认允许，编辑后按内容审核规则处理                         |
| 审核内容、管理用户、配置站点 | 仅站主，不作为普通投稿白名单功能开放                       |

统一图片权限只使用 image.upload 一项；可单独禁止某用户提交某栏目，但不会为文章插图、项目封面再建立不同上传权限。

## 白名单和黑名单的不同用途

1. 功能用户名单：例如允许用户甲上传图片，禁止用户乙提交友链。
2. 账号封禁：全局禁止该账号使用登录后的业务功能，失效已有会话；不承诺阻止其匿名访问公开页面。
3. 项目网站名单：限制项目卡片允许指向的网站，与用户白名单独立。建议同时支持网站黑名单用于排除某域名或路径；同一地址命中允许和禁止规则时，禁止优先。

用户以站内 ID 与 GitHub provider account ID 关联，不用可修改昵称作为授权依据。域名规则使用解析后的精确主机及明确的子域名/路径规则，不能做简单字符串包含匹配。

## 权限计算建议

对普通用户的业务请求按以下顺序判断，任一步失败均拒绝对应操作：

1. 身份有效且账号未被封禁。
2. 是否在该能力黑名单：命中即拒绝。
3. 是否有显式允许：有则取得该能力；否则采用角色默认权限，未知能力默认拒绝。
4. 验证内容归属、项目网站限制和其他业务条件。
5. 涉及上传时，验证统一图片权限、容量预留和单文件限制。
6. 内容投稿进入 AI/人工审核；未配置 AI 时转人工。点赞/取消点赞是免审操作，不进入内容审核队列。站主本人发布按已确认规则免审。

允许某项能力只允许发起操作，不绕过资源容量、项目网站规则、内容归属或适用的审核要求。功能名单与账号封禁作用不同；用户被封禁后单项白名单不能恢复其业务访问。

示例：用户可提交文章但没有上传权限，可以提交纯文字；项目发布在用户白名单中但链接不在允许网站内，仍拒绝；图片上传被允许但容量已满，仍拒绝。

## 管理后台

- 用户列表：GitHub 账号、状态、图片已用/总容量；可筛选封禁用户或有自定义权限的用户。
- 用户详情：账号状态、按功能的三态权限、上传容量、规则备注与操作记录。
- 功能名单：按功能查看允许/禁止的用户，与用户详情编辑同一数据源。
- 项目网站规则支持允许、禁止、包含子域名和启停。网址检查与规则配置见[项目网站白名单](./publishing-rules.md#项目网站白名单)。
- 有效权限解释：显示最终能否操作及原因，如“继承普通用户权限”“单用户禁止”“账号封禁”“容量不足”。

默认永久生效，是否支持临时封禁或限时授权待确认；不预设批量修改和复杂角色继承。

## 服务端与数据建议

- Next.js 统一执行权限检查；Route Handlers、Server Actions、上传签名和提交接口共用规则，前端仅展示结果。
- 数据修改仍按作者 ID 限定查询范围，不能只通过模块权限检查就允许修改任意内容。
- 权限变更在后续请求生效，不仅保存在长期 JWT 中；必要时使用权限版本使缓存失效。
- 审核结果准备公开内容前重新检查账号和提交资格；被封禁或撤权的待审内容不因旧任务完成而自动发布。
- Python 不决定用户授权，也不直接写权限表。
- 站主身份通过明确配置的可信 GitHub ID 初始化，不使用“第一个登录者自动成为管理员”。普通用户不能提交自己的角色或配额。
- 避免站主通过普通用户页面封禁自己或移除最后的管理入口；账号封禁、权限和额度修改记录操作者及修改前后值。

候选模型：User（账号状态）、UserPermissionOverride（用户 + 能力唯一，ALLOW/DENY；无记录即继承）、UserStorageQuota（上限、已用和预留字节）、ProjectSiteRule（ALLOW/DENY + 域名及路径）、PermissionAuditLog。

统一 image.upload 权限保存在权限表，容量仅保存在配额表，不另设一个独立上传开关造成两个授权来源。替代此前 UserUploadPolicy 将开关与配额混放的候选设计。

## 待明确的边界

- 封禁或撤权后，已发布内容默认建议保留，站主可单独下架；不自动删除文件。
- 是否允许临时封禁/限时授权，首版可先不做。
- 每用户容量、单文件大小、全站图片容量已确认支持后台设置和变更；初始值及上传速率规则仍待设置。
- 已确认站主本人发布免审；普通用户白名单不带来免审资格。
